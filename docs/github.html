The GitHub guide.

Git is the tool; GitHub is the place teams meet around it. This chapter covers everything that belongs to the place: pull requests, forks, Issues, Actions, releases, Pages, and the shortcuts experienced users lean on daily.

Your first repository, on the website

The plus button at the top right, then New repository. Four choices matter, and the site makes three of them for you:

NameShort, lowercase, hyphens: weather-app, not WeatherAppFinal2
Add a READMEYes. It becomes the repository's front page and your first commit
Add .gitignorePick your language; build output and dependencies stay out of history from day one
Choose a licenseMIT if unsure. No license means others may read but not legally reuse

Then bring it to your machine with git clone <url> and you are working. Starting from a folder already on your machine instead? The Start page covers that direction.

The words nobody explains

GitHub assumes you know these. Two minutes settles them forever:

repositoryA project and its entire history, as one unit. Everyone says repo
README.mdThe front page. GitHub renders it automatically on the repository home
.md, MarkdownPlain text with light marks: # makes a heading, **bold**, - makes a list, [text](url) makes a link. GitHub renders it everywhere
.gitignoreThe list of things Git must never track: build output, dependencies, secrets
LICENSEThe legal terms of reuse. MIT is the everyday permissive choice
public, privatePublic: everyone reads, only you write. Private: invitation only
starA bookmark and a thank-you in one; stars rank repositories
watchSubscribe: issues, pull requests, and releases reach your notifications
clone vs forkClone copies a repo to your machine; fork copies it to your GitHub account
issueA tracked conversation about one bug or one request
default branchUsually main: what visitors see and what pull requests target
gistA single shareable file with its own URL and history, at gist.github.com
organizationA shared account for a team; repositories live under it, members hold roles

Pull requests, done properly

A pull request is a conversation about a branch. The mechanics are three commands and a link:

git switch -c fix-login-timeout
git push -u origin fix-login-timeout
gh pr create --fill

Or click the yellow "Compare & pull request" banner GitHub shows after the push. Open it as a draft if it is not ready for review.

What separates a good PR from a painful one: it is small enough to review in one sitting, its description says why rather than what, and it stays alive by responding to review with new commits, not force pushes, until the reviewer approves. On your own PR branch, rebasing to clean up before merge is normal; add Fixes #123 to the description and the issue closes itself on merge.

Review one locally with check out a pull request; keep your branch current with rebase onto main.

The life of a pull request

Forks and the open source flow

A fork is your own copy of someone else's repository, the door to contributing anywhere on GitHub:

gh repo fork <owner>/<repo> --clone

Fork, clone, branch, commit, push to your fork, open the PR against the original. The original repository is conventionally the remote named upstream; keep your fork in sync before every new branch.

Issues that get fixed

An issue that names the version, the exact steps, what happened, and what you expected gets fixed. One topic per issue, real error text pasted as text, and a minimal reproduction beats a paragraph of description. Reference code precisely: press y on any file view to get a permalink to that exact commit, then click a line number to link the line.

GitHub Actions

Actions runs commands for you on every push: tests, checks, deploys. One file in the repository is the whole setup. This very site validates its data and house style on every commit with a workflow of a dozen lines:

mkdir -p .github/workflows

A minimal workflow file, .github/workflows/checks.yml: run on push, check out the code, run your test command. Start from this repository's real one. Two habits worth copying from day one: give workflows only the permissions they need, and pin third-party actions to a commit hash, not a tag.

Releases

A release is a tag with a face: notes, downloadable assets, a permanent link.

git tag -a v1.0.0 -m "First stable release"
git push origin v1.0.0
gh release create v1.0.0 --generate-notes

--generate-notes writes the changelog from merged PRs since the last release.

GitHub Pages

Free hosting for static sites, straight from a repository. Settings, Pages, choose the branch and folder, done: the page you are reading is served exactly this way from the docs/ folder. Project sites live at <user>.github.io/<repo>; name a repository <user>.github.io and it becomes your root site.

The gh CLI

GitHub's command line brings the site to your terminal. The handful that pay for themselves daily:

gh auth login
gh repo create <name> --public --source . --push
gh pr checkout <number>
gh pr status
gh run watch

Power moves

Press . in any repository and it opens in a browser VS Code. Press t to fuzzy-find any file, / to search code. Append .patch to any commit URL for the raw patch, or #L10-L20 to link exact lines. Blame view has a "view blame prior to this change" button that digs through reformats. Your profile README is a repository named after your username. And drag any image into an issue or PR comment to host it instantly.

Protect the branch

On a team, nobody writes to main directly, not even you. Settings, Branches, one ruleset: require a pull request, require the checks to pass. From that moment main cannot break by accident, only by review. Assign reviewers by path with a CODEOWNERS file:

printf "docs/ @<reviewer>\n" > .github/CODEOWNERS

Whoever owns a path is requested automatically on every pull request that touches it.

Your profile is a repository

Create a repository named exactly your username and its README becomes the top of your profile. Pin the six repositories that represent you best. And know the one rule of the contribution graph: commits count only when their author email matches an address on your GitHub account, which is why a wrong git identity quietly erases your work from it.

Where GitHub ends

Everything above is the host, not the tool. The same Git speaks to GitLab, Bitbucket, and AWS CodeCommit, to Azure DevOps, to any new host with full history, and to no host at all. Learn Git once; the platforms are details.
