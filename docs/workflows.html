How teams run Git.

Five workflows cover almost all real work. Pick the one that matches your situation; they are identical on every host.

Working alone

No branches required, no ceremony. Commit at every working state, push as your backup, tag what you might return to.

git add -A && git commit -m "<message>" && git push

The one habit worth adding even alone: branch before an experiment, so abandoning it is git switch main instead of an archaeology dig.

Feature branch flow

The default for teams everywhere. main stays releasable; every change arrives by pull request.

git switch main && git pull
git switch -c <change-name>
git push -u origin <change-name>

Then open the pull request and let review and checks do their work; the life of a pull request walks it visually. Branch behind main? Rebase onto main. Merged? Delete the branch without sentiment.

Fork flow

For repositories you do not have write access to, which is all of open source. Your fork is yours; the pull request crosses the boundary.

gh repo fork <owner>/<repo> --clone
git switch -c <change-name>
git push -u origin <change-name> && gh pr create --fill

Sync the fork before every new branch, or you will build on stale ground.

Trunk-based development

The high-velocity variant: branches live hours, not weeks. Small changes merge to main daily behind feature flags; long-lived branches and their merge agonies disappear. It demands discipline the tooling cannot supply: tiny PRs, fast review, and CI the team actually trusts.

git config --global pull.rebase true

With everyone integrating constantly, rebase-by-default keeps history a straight line worth reading.

Releases and hotfixes

A release is a tag; a hotfix is a branch from that tag.

Releases are tags on main's line. A fix branches from the tag, ships as its own tag, and merges back so main keeps the cure.

git tag -a v2.1.0 -m "<release note>" && git push origin v2.1.0
git switch -c hotfix-2.1.1 v2.1.0

Fix, tag v2.1.1, ship, then merge the hotfix back to main so the bug stays dead. Cherry-pick carries a main fix onto a release line when work happened in the other order.

The rules that keep teams safe

Never rewrite a branch others build on; rewrite your own PR branches freely with force-with-lease, never with plain force. Pull with rebase so your local commits sit on top. Protect main so nothing lands without review and green checks. And when anything is unclear, git status first: it names the state you are in and, usually, the way out.
